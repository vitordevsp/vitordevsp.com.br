## O que fazer

1. Tipar `__children` explicitamente em `src/lib/notion/features/blocks/types.ts`:
   ```ts
   export type AnyNotionBlockWithChildren = AnyNotionBlock & {
     __children?: AnyNotionBlock[]
   }
   ```
   Eliminar o `(parent as any).__children = children` em `blocks/index.ts`.

2. Trocar o loop sequencial do modo `deep: true` por busca paralela **com limite de concorrencia**, nao `Promise.all` cego.

3. Tratar 429 respeitando o header `Retry-After` (ver referencia abaixo). No minimo, nao crashar — idealmente, retry com backoff.

4. Formalizar o contrato de paginacao no comentario do wrapper (`start_cursor` + `has_more` + `next_cursor`, default 10, max 100). O codigo ja esta correto; so documentar.

5. Preservar o shape consumido por `PageRenderer` (o `BaseBlock` local dele ja declara `__children`).

## Contexto da API

- Rate limit oficial: **3 req/s em media**, com bursts. 429 retorna `Retry-After` em segundos. Ver [docs/resources/notion-docs/reference/request-limits.md](../../../resources/notion-docs/reference/request-limits.md).
- Em paginas com muitos toggles/listas aninhadas, `Promise.all(withChildren.map(...))` dispara N requests simultaneos e cruza o limite facilmente. Limitar a ~3 em paralelo (ex.: `p-limit(3)` ou implementacao propria pequena) evita 429 sem sacrificar ganho.
- [docs/resources/notion-docs/reference/get-block-children.md](../../../resources/notion-docs/reference/get-block-children.md) — endpoint consumido.

## Nao fazer

- Nao introduzir lib nova sem avaliar — um `p-limit` caseiro de ~10 linhas resolve.
- Nao mudar a assinatura publica de `getAllBlockChildren`.
