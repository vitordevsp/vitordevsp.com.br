## O que fazer

A partir da versao `2025-09-03`, databases passaram a expor `data_sources` e o endpoint canonico de query virou `POST /v1/data_sources/{id}/query`. `databases.query` ainda existe mas nao e mais o caminho principal em databases com multiplas sources.

Ajustar `src/lib/notion/features/databases/index.ts`:

1. Trocar `notion.databases.query({ database_id, ... })` por `notion.dataSources.query({ data_source_id, ... })` (nome do metodo no SDK pode variar — verificar `@notionhq/client` instalado).
2. Adicionar funcao auxiliar para resolver `data_source_id` a partir de um `database_id` quando o chamador so tiver o ID do database (usar `databases.retrieve` e pegar o primeiro `data_sources[0].id`, ou expor escolha quando houver mais de um).
3. Ajustar a variavel de ambiente: hoje temos `NOTION_DATABASE_ID`. Avaliar se deve virar `NOTION_DATA_SOURCE_ID` direto (mais simples, menos request) ou manter `DATABASE_ID` e resolver a source em runtime (mais tolerante).
4. Manter `getDatabaseProps` apontando para `databases.retrieve` (metadata do database continua fazendo sentido a nivel de database).

## Por que

- [reference/query-a-data-source.md](../../../resources/notion-docs/reference/query-a-data-source.md) e o endpoint moderno.
- [reference/database.md](../../../resources/notion-docs/reference/database.md) e [reference/data-source.md](../../../resources/notion-docs/reference/data-source.md) explicam a distincao.
- Jardim digital e cursos tendem a ter multiplas views/sources num mesmo database — ficar em `databases.query` silenciosamente escolhe a primeira source e limita o que podemos expor.
